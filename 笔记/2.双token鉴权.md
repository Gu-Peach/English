首先前端发出请求时会经过请求拦截器，从 Pinia user store（localStorage 持久化）读 accessToken，自动塞进`Authorization: Bearer xxx` 请求头。

```text
Authorization: Bearer eyJhbGciOi...
               ↑[0]   ↑[1]
按空格切开后取第 2 段——"Bearer " 前缀是给中间层/服务端识别"这是什么认证方式"用的，
将来换成 Basic（账号密码 base64）也是同一个头，格式不同。
```

然后axios将请求转发后端，后端一些接口会设置guard鉴权，guard鉴权负责判断：
① 有没有 Authorization 头？ → 没有：401 "你是偷子???"
② 取出 token，verify() → 验签名（防伪造/篡改）+ 验 exp（过期）
任一失败：401 "token已过期或无效"
③ decoded.tokenType === 'access'？ → 不是：401（防 refreshToken 冒充）
④ 全过 → request.user = decoded，return true → 进 controller → service → 返回数据

## accessToken 过期

触发点：后端 auth.guard.ts L20`verify()` 发现 exp 已过 → 抛异常 → catch 转`UnauthorizedException` → HTTP 401
处理点：前端 apis/index.ts L30-68 响应拦截器的失败回调，按行内流程：
通过refreshTokenApi接口获取新的 accessToken存放到 Pinia user store（localStorage 持久化），然后将新的 accessToken 放到请求头中，重新发送请求

## refreshToken 也过期 → 强制登出

触发点：后端 user.service.ts L103-127`refreshToken()` 方法
过期后重新登录

## 问题：当前实现里 refreshToken 每次刷新都会一起换新 ，而且由此引出两个真实的安全后果

1.只要用户每 7 天内活跃一次，理论上永远不用重新登录 2.旧的 refreshToken 没有被作废

## 生产环境的补法（了解方向即可）

| 手段             | 做法                                                                                              | 解决什么                          |
| ---------------- | ------------------------------------------------------------------------------------------------- | --------------------------------- |
| 轮换 + 黑名单    | 刷新时把旧 refreshToken 的 `jti`（唯一 ID）存入 Redis 黑名单（TTL=剩余有效期），verify 时多查一次 | 旧 token 用一次即废，重放立刻识别 |
| 一次性轮换检测   | 每次刷新签发新 refreshToken 并入库；旧的被再次使用 → 判定泄露，吊销整条会话链                     | 偷旧 token 的人和真用户谁先用谁赢 |
| 绝对上限         | payload 里加 `sessionExp`（如登录时刻+30天），刷新时新 token 的 exp 取 `min(now+7d, sessionExp)`  | 滑动窗口封顶，最多 30 天必须重登  |
| 敏感操作二次认证 | 支付/改密码时要求重新验密                                                                         | 即使会话被劫持也有一道闸          |
